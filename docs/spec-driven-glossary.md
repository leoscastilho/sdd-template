# Spec-driven development: a plain-language glossary

This page explains the words used across this repository and its dashboard. It is about the *way of working*, not about the product. If you can read a checklist, you can read a spec; this glossary is here so the jargon never gets in the way.

## The big idea

| Term | Plain meaning |
| --- | --- |
| **Spec-driven development (SDD)** | A way of building software where the written description of what the system must do comes first, and the code is derived from it. The documents are the source of truth; the code is a consequence. If the code and a document disagree, the document is fixed or the code is, in the same sitting. |
| **Spec** | Short for specification: one markdown file that describes one thing (a feature, an architectural rule, an interface, or a decision) precisely enough that someone could build and test it without asking questions. Every spec has an id, a status, and a header block (see *frontmatter*). |
| **Corpus** | All the specs together, as one body of knowledge. The dashboard is a view of the corpus. |
| **Source of truth** | The one place a fact is allowed to live. In SDD the spec is the truth for behaviour, the contract is the truth for interfaces, and the ADR is the truth for decisions. Everything else (code, dashboards, indexes) is derived and can be regenerated. |
| **Derived** | Produced from something else and never edited by hand. Generated code, the spec index and this dashboard are derived; if they look wrong, fix the source and regenerate. |
| **Precedence** | The rule for which document wins when two disagree. Here: an accepted decision beats everything; a contract beats a feature spec on interface shape; a feature spec beats an architecture spec on behaviour; the original design narrative loses to any later spec. |

## The kinds of documents

| Term | Plain meaning |
| --- | --- |
| **Product spec** | Describes the why and the who: vision, personas, vocabulary. Ids start with `P-`. |
| **Architecture spec** | Describes a cross-cutting rule or mechanism that many features rely on: how data is stored, how sync works, how security is enforced. Ids start with `ARCH-`. |
| **Feature spec** | Describes one thing a user can do, end to end: the behaviour, its empty/loading/error states, what data it stores, and the tests that prove it. Ids start with `F-`. |
| **Contract** | The exact shape of an interface between two parts of the system: the HTTP API (OpenAPI), the WebSocket messages, the LaTeX render service API, the document-type registry. Both sides of an interface are written against the contract; it changes before the code does. Ids start with `C-`. |
| **ADR (Architecture Decision Record)** | A short document that records one decision: the situation, what was chosen, what it costs, and every alternative that was considered with the reason it lost. ADRs are numbered (`ADR-0007`) and never edited once accepted; a new ADR supersedes an old one instead. |
| **Open question** | Something the team has not decided yet, written down with the options, a recommendation, and what it holds up. Lives in one file so nothing is decided by accident. Referred to as `Q` plus a number. |
| **Roadmap** | The ordered list of milestones and the work items in each. One milestone is marked *current*. |
| **Glossary** | The canonical vocabulary. The product glossary fixes the words for the domain (what a "laudo" is); this page fixes the words for the method. |
| **Template** | A skeleton file (`_template.md`) that new specs are copied from so every spec has the same sections. Templates are not specs themselves. |
| **Index** | A generated table of every spec with its status. Regenerated by a command; never edited by hand. |
| **Design narrative** | The original long-form write-up the project started from. Kept verbatim for its reasoning; where later specs contradict it, the later spec wins. |

## Anatomy of a spec

| Term | Plain meaning |
| --- | --- |
| **Frontmatter** | The block between two `---` lines at the top of a spec. It holds the machine-readable facts: id, title, type, status, which code paths it governs, which specs it depends on, which decisions it applies, and when it was last reviewed. Tools read it; people mostly skip it. |
| **Id** | A short, unique, stable name for a spec, such as `F-DOCUMENT-EDITOR` or `ADR-0003`. Ids are how specs refer to each other, how commits cite them, and how the dashboard links them. The prefix tells you the kind. |
| **Title** | The human-readable name shown next to the id. |
| **Type** | One of product, architecture, feature, contract or decision. Mirrors the id prefix. |
| **Status** | Where the spec is in its life. See *Lifecycle* below. |
| **Implements** | The list of code paths this spec governs, written as globs (see below). This is the seam that ties documents to code: when a file under one of these paths changes, this spec must be checked. |
| **Depends on** | The other specs this one relies on being true. If a dependency changes, this spec may need a look. |
| **Dependents** (or *depended on by*) | The reverse: specs that rely on this one. The dashboard computes this; it is not written by hand. |
| **Decisions** | The ADRs this spec applies. Adding an ADR id here is how a decision is *propagated* into the specs it affects. |
| **Cited by** | The reverse of *decisions*: the specs that apply a given ADR. |
| **Last reviewed** | The date someone last confirmed the spec still describes reality. A spec that has not been reviewed for a while is *stale*. |
| **Derived from** | A line naming the sections of the design narrative (or other specs) a spec was written from, so its reasoning can be traced. |
| **Acceptance criteria** | The list of testable statements that define "done", usually written as *Given* a situation, *when* something happens, *then* an outcome is observed. Each criterion becomes the name of a test. A feature is *implemented* only when every criterion has a passing test. |
| **Ruled out** | Options that were considered and rejected, each with its reason. These are hard constraints: nobody may reintroduce a ruled-out option without a new ADR that overturns it. In ADRs the same section is called *Alternatives considered*. |
| **Out of scope** | Things the spec deliberately does not cover. Unlike *ruled out*, they are not forbidden, just not part of this spec. |
| **Behaviour** | The plain-language description of what happens, screen by screen or endpoint by endpoint. |
| **Data sensitivity** | What a feature stores, encrypts and logs. Every field here is clinical data. |

## Linking documents to code

| Term | Plain meaning |
| --- | --- |
| **Glob** | A path pattern with wildcards. `*` matches any run of characters within a name; `**` matches any depth of folders. `apps/api/src/documents/**` means "everything under the documents folder of the API". Specs use globs to name the code they govern without listing every file. |
| **Claim** | A spec *claims* a code path by listing a glob in its *implements* list. A file is *claimed* when at least one spec's glob matches it. |
| **Unclaimed code** | A code file that no spec's glob matches. It has no governing document, so nobody can say what it is supposed to do. The audit reports it as a problem to fix by adding a glob to the right spec. |
| **Governing spec** | The spec whose glob matches a given file. When that file changes, the governing spec must be revisited in the same session. |
| **Traceability** | Being able to walk from any line of code to the spec that requires it, and from any acceptance criterion to the test that proves it. The *implements* globs and the criterion-named tests make this mechanical. |
| **Drift** | When code and its governing spec no longer agree, typically because code changed and the spec was not updated. The drift check compares changed files against changed specs and refuses to finish a session while drift exists. |
| **Dangling reference** | An id mentioned in a spec's *depends on* or *decisions* that no spec actually declares. Usually a typo or a renamed spec. |
| **Overlap** | A file claimed by more than one spec. Allowed when deliberate (a feature and an architecture spec sharing a folder), flagged so it can be checked. |
| **Empty claim** | A spec whose status says it is being or has been built, but whose globs match no files. Either the status is wrong or the code lives somewhere else. |
| **Generated output** | Files produced by a tool (the Prisma client, the spec index, the dashboard), kept in folders named `__generated__` or written by a `make` target. Never edited by hand; regenerated with a command. |
| **Contract-first** | Designing the interface (the contract) before the code on either side of it, so both sides are written and reviewed against the same source. |

## Deciding things

| Term | Plain meaning |
| --- | --- |
| **Blocks** | On an open question: the specs that cannot leave *draft*, or the work that cannot start, until this question is answered. A question that blocks something is shown as *blocking*. |
| **Affects** | On an open question or ADR: the specs whose wording changes once the answer is known, without being blocked by it. |
| **Recommendation** | The option the author suggests, written down with the question so a decision can be made quickly. A recommendation is not a decision. |
| **Decide** | The act of choosing an option. It always produces an ADR, removes the question from the open list, and updates every spec the question listed. Nobody decides by quietly picking an option in code. |
| **Propagate** | After a decision, editing each affected spec so it states the decision as fact and cites the ADR, and removing the "still open" wording. |
| **Resolved** | A question that has been decided. It moves to a table that points at the ADR that answered it. |
| **Supersede** | To replace an accepted ADR with a newer one. The old ADR keeps its text, is marked *superseded*, and points at its replacement. This is the only way to change a past decision. |
| **Proposed / accepted / superseded / rejected** | The four states of an ADR: suggested but not yet agreed; agreed and binding; replaced by a later ADR; considered and turned down. |
| **Hard constraint** | A rule that tools and reviewers enforce, not a preference. Everything under *ruled out* is one. |

## Lifecycle and status words

| Term | Plain meaning |
| --- | --- |
| **Draft** | Being written. May contain gaps and open questions. Not ready to build from. |
| **Approved** | Complete enough to build from. No open question blocks it. |
| **Implementing** | Someone is actively building it; the claimed code paths are starting to exist. |
| **Implemented** | Built, and every acceptance criterion has a passing test. The spec and the code agree. |
| **Deprecated** | No longer applies. Kept for history and points at what replaced it. |
| **Stale** | Not reviewed for longer than the agreed window. Not necessarily wrong, but nobody has confirmed it recently. |
| **Milestone** | A group of roadmap items that, together, produce something demonstrable. Exactly one is *current*. |
| **Blocking** | Holding something up. Used for open questions that keep a spec in draft. |

## Checks and automation

| Term | Plain meaning |
| --- | --- |
| **Lint (spec-lint)** | An automatic check that every spec has valid frontmatter, a unique id, dates in the right format, and references to ids that exist. Runs before every commit. |
| **Audit (spec-audit)** | An automatic sweep that lists unclaimed code, globs that match nothing, and status counts. The dashboard's traceability page shows the same information. |
| **Drift check (spec-drift)** | Compares the code files changed in a session with the specs changed in that session and reports code whose governing spec was not touched. |
| **Security quick-scan** | A fast, pattern-based check for obvious security mistakes (hard-coded keys, unsafe HTML, raw LaTeX control sequences outside the renderer, unsafe raw SQL) that runs on every edit and before every commit. |
| **Security audit** | A deeper, reasoned review of code against five categories of flaw (input reaching LaTeX unescaped, secrets, IDOR on drafts, XSS, PII in logs), run on each feature before it is called implemented and on the whole repository at the end of each milestone. Critical and high findings block completion. |
| **Hook** | A small script the tooling runs automatically at a moment in the workflow: when a session starts (prints orientation), before a file is edited (refuses edits to generated files), after a file is edited (lints it, records it), and when a session tries to end (runs the drift check). Hooks make the rules hard to forget. |
| **Pre-commit** | A hook that runs lint, drift and the quick-scan on the files about to be committed and refuses the commit if any fail. |
| **Ledger** | The list of files touched during one working session, kept so the end-of-session drift check knows what to compare. |
| **Gate** | A check that must pass before work may move to the next state. The security audit is a gate on *implemented*. |

## Who does what

| Term | Plain meaning |
| --- | --- |
| **Orchestrator** | The main assistant session. It reads specs, plans, writes instructions for the specialised agents, reviews their output, reconciles specs and talks to the user. It does not write application code itself. |
| **Agent** | A specialised assistant given one bounded job and a written brief. Examples: the *coder* (writes code and tests from a brief), the *ui-coder* (presentational React and CSS from a surface brief), the *spec-editor* (applies wording changes across specs), the *spec-reviewer* (checks code against acceptance criteria), the *security-auditor* (looks for flaws), the *test-runner* (runs commands and reports only what matters), the *scribe* (drafts commit messages). |
| **Brief** | The self-contained instruction an agent receives: which spec, which decisions, which paths it may touch, and what "done" looks like. |
| **Skill (slash command)** | A scripted workflow the user can start by name, such as `/decide` (write an ADR and propagate it) or `/implement` (build a spec end to end). |
| **Reconcile** | Bringing a spec back into agreement with code that changed, in the same session as the change. |
| **The user** | The person who owns the decisions. Agents recommend; the user decides. |

## Reading the dashboard

| Label | What it means |
| --- | --- |
| **Blocking** (on a question) | At least one spec cannot leave draft until this is decided. |
| **No recommendation / no options listed** | The question is missing the fields that make it quick to decide. |
| **Ready to build** (roadmap item) | Every spec the item references is approved and no open question is named. |
| **Spec is draft** | At least one referenced spec is still a draft. |
| **Needs decision** | The item names an open question. |
| **In progress** | A referenced spec is marked implementing. |
| **Built, untick** | Every referenced spec is implemented but the roadmap checkbox has not been ticked yet. |
| **Done** | The checkbox is ticked. |
| **No spec ref** | The item names no spec or decision, so its state cannot be derived. |
| **Claimed / unclaimed** | Whether a code file is matched by some spec's globs. |
| **Nothing on disk yet** | A glob that matches no file. Normal for specs that are approved but not yet built. |
| **Links to / linked from** | Explicit markdown links between files. |
| **Mentions** | Files whose text names this spec's id, even without a link. In this corpus most cross-references are mentions. |
| **Depends on / depended on by / decisions / cited by** | The frontmatter relationships described above. |
| **Not referenced anywhere** | A file with no inbound link and no mention of its id. Templates and readmes are expected here. |
