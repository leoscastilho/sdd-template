# Specs — the source of truth

> New to spec-driven development? [docs/spec-driven-glossary.md](../docs/spec-driven-glossary.md) explains every term used here and in the dashboard in plain language.

This repository is **spec-driven**: no human writes code. Every line under `apps/`, `packages/`, `services/` and `infra/` is derived by an agent from the documents in this folder. If the code and a spec disagree, **the spec is right and the code is a bug** — unless the spec is stale, in which case fixing the spec is the first step, not the last.

## Layout

| Folder | What lives here | Normative? |
| --- | --- | --- |
| `00-product/` | Vision, glossary, personas. Why the product exists and the words we use (derived from `PRODUCT.md`). | Yes for vocabulary |
| `01-architecture/` | Cross-cutting technical design: monorepo, deploy (compose/Easypanel), data and encryption, LaTeX render sandbox, security, observability, testing. | Yes |
| `02-features/` | One file per user-facing capability, each with acceptance criteria. The unit of implementation. | **Yes — highest for behaviour** |
| `03-contracts/` | Interfaces: OpenAPI for `/api`, WebSocket messages on `/ws`, the LaTeX render service API, the document-type registry. Updated *before* the code on either side. | **Yes — highest for interfaces** |
| `04-decisions/` | Architecture Decision Records (ADRs). Immutable once accepted; supersede, don't edit. | **Yes — highest for "why"** |
| `OPEN-QUESTIONS.md` | Everything not yet decided, with a recommendation each. Blocks implementation of whatever it touches. | — |
| `ROADMAP.md` | Milestones and their ordering. The current milestone is marked. | — |
| `INDEX.md` | Generated by `make spec-index`. Do not edit by hand. | — |

## Precedence when documents disagree

1. An **accepted ADR** wins on any decision it covers.
2. A **contract** wins on any interface shape.
3. A **feature spec** wins on behaviour.
4. An **architecture spec** wins on cross-cutting mechanics.
5. `PRODUCT.md` (root) and `01-architecture/system-overview.md` are the original product and architecture narratives, kept for rationale; where a later spec contradicts them, the later spec wins and the contradiction goes in `OPEN-QUESTIONS.md` until resolved by an ADR.

"Ruled out" sections anywhere in these documents are **hard constraints**, not suggestions. Do not reintroduce a rejected option without a new ADR.

## Frontmatter (required on every spec)

```yaml
---
id: F-DOCUMENT-EDITOR       # unique. Prefixes: P- product, ARCH- architecture, F- feature, C- contract, ADR-NNNN decision
title: Document editor
type: feature               # product | architecture | feature | contract | decision
status: draft               # see lifecycle below
implements:                 # code paths this spec governs. Globs. `**` allowed.
  - apps/api/src/documents/**
  - apps/web/src/modules/documents/**
depends_on: [F-LATEX-RENDER-SERVICE, C-OPENAPI, C-WS-MESSAGES]
decisions: [ADR-0003]
last_reviewed: 2026-09-12
---
```

`implements` is the traceability seam. The drift hook uses it to tell the agent *which* spec to revisit when a file changes, and the audit finds code no spec claims. Keep it accurate.

## Lifecycle

| Status | Meaning |
| --- | --- |
| `draft` | Being written. May contain TODOs and open questions. Not implementable. |
| `approved` | Complete enough to implement. No unresolved questions that block it. |
| `implementing` | An agent is actively building it. `implements` paths exist. |
| `implemented` | Acceptance criteria verified by tests. Spec and code agree. |
| `deprecated` | Superseded. Kept for history; points to its replacement. |

ADRs use `proposed | accepted | superseded | rejected`.

## How change flows

- **Planned change** → edit the spec first (or write a new one with `/spec-new`), get it to `approved`, then `/implement`.
- **Discovery during implementation** (the spec was wrong, incomplete, or a better option appeared) → fix the spec **in the same session**, then continue. The Stop hook will refuse to let a session end with code changes whose governing spec was not touched.
- **A decision** (choosing between options, ruling something out) → `/decide` writes an ADR, resolves the open question, and updates the specs it affects.
- **Bug fix** → if the spec was silent, add the acceptance criterion the bug violated. A bug is a missing sentence in a spec.

## Writing a good feature spec

Use `02-features/_template.md`. The parts that matter most:

- **Acceptance criteria** in Given/When/Then form, each independently testable. These become the test names.
- **Empty / loading / error states** — the preview keeps the last good PDF while compiling; validation and class errors are shown where they apply.
- **Data**: what is stored (drafts are ciphertext), what is never logged, what never leaves the browser.
- **Out of scope** and **ruled out** — what the agent must *not* build.
- **Open questions** — anything unresolved, mirrored into `OPEN-QUESTIONS.md`.

## Tooling

```
make spec-lint     # frontmatter valid, ids unique, references resolve
make spec-index    # regenerate INDEX.md
make spec-drift    # code changed but governing spec not (also runs at Stop and pre-commit)
make spec-audit    # unclaimed code, dangling implements globs
```
